# Synthetic Data Model

This document defines the raw CSV contract generated by `data/generate.py`.
It is a simplified Bitcoin-style model designed for deterministic local data
generation, validation, UTXO reconciliation, and analytical demonstrations;
it is not a complete representation of the Bitcoin protocol.

## Conventions

- The four files are relational: `blocks` contain `transactions`, and
  transactions contain `inputs` and `outputs`.
- Monetary fields use integer satoshis. For clean generated records,
  `total_input_sats = total_output_sats + fee_sats`.
- An input normally references a prior output using
  `(previous_tx_hash, previous_output_index)`. The `previous_tx_hash` value
  `genesis` is a documented sentinel for a seeded input with no prior generated
  output.
- Hashes, addresses, miner names, and values are synthetic. They are suitable
  for local demonstrations and tests, not for interpreting real blockchain
  activity.

For how these fields are validated, reconciled, and published as Iceberg
tables, see [Data Transformations](data_transformations.md).
For generation mechanics, output directories, and reproducibility notes, see
[Synthetic Data Generation](data_generation.md). For deliberate failure cases,
see [Corruption Fixtures](corruption_fixtures.md).

## blocks
blocks.csv

One row per block.

| Column              | Type      | Description                     |
| ------------------- | --------- | ------------------------------- |
| block_hash          | string    | Unique identifier for the block |
| block_height        | int       | Sequential block number         |
| previous_block_hash | string    | Hash of previous block          |
| timestamp           | timestamp | Time block was mined            |
| miner               | string    | Mining pool (or dummy name)     |
| difficulty          | double    | Mining difficulty               |
| nonce               | long      | Proof-of-work nonce             |
| size_bytes          | int       | Serialized block size           |
| transaction_count   | int       | Number of transactions in block |

example:
```
block_hash,block_height,previous_block_hash,timestamp,miner,difficulty,nonce,size_bytes,transaction_count
000001abc,800000,000000fff,2025-01-01T00:00:00Z,F2Pool,82.6,234234234,1425678,2145
000001abd,800001,000001abc,2025-01-01T00:09:55Z,AntPool,82.6,78342345,1398888,1892
```

## transactions
transactions.csv
one row per Bitcoin transaction

| Column            | Type      | Description                 |
| ----------------- | --------- | --------------------------- |
| tx_hash           | string    | Transaction ID              |
| block_hash        | string    | Foreign key to blocks       |
| timestamp         | timestamp | Transaction timestamp       |
| fee_sats          | long      | Transaction fee in satoshis |
| size_bytes        | int       | Transaction size            |
| input_count       | int       | Number of inputs            |
| output_count      | int       | Number of outputs           |
| total_input_sats  | long      | Total input value           |
| total_output_sats | long      | Total output value          |

example:
```
tx_hash,block_hash,timestamp,fee_sats,size_bytes,input_count,output_count,total_input_sats,total_output_sats
tx001,000001abc,2025-01-01T00:00:05Z,2500,420,2,3,15000000,14997500
```
## inputs
inputs.csv

Every transaction can have many inputs.

Think of this as a child table of `transactions`.

| Column                | Type   | Description                 |
| --------------------- | ------ | --------------------------- |
| input_id              | string | Unique input ID             |
| tx_hash               | string | Parent transaction          |
| input_index           | int    | Position within transaction |
| previous_tx_hash      | string | Transaction being spent     |
| previous_output_index | int    | Output being spent          |
| address               | string | Sender address              |
| value_sats            | long   | Value consumed              |

example:
```
input_id,tx_hash,input_index,previous_tx_hash,previous_output_index,address,value_sats
i1,tx001,0,tx000,1,bc1abcd...,10000000
i2,tx001,1,tx555,0,bc1xyz...,5000000
```

## outputs
outputs.csv

every transaction can also have multiple outputs

| Column       | Type    | Description                        |
| ------------ | ------- | ---------------------------------- |
| output_id    | string  | Unique output ID                   |
| tx_hash      | string  | Parent transaction                 |
| output_index | int     | Position within transaction        |
| address      | string  | Receiver address                   |
| value_sats   | long    | Amount received                    |
| spent        | boolean | Whether this output has been spent |

example:
```
output_id,tx_hash,output_index,address,value_sats,spent
o1,tx001,0,bc1receiver1,8000000,true
o2,tx001,1,bc1receiver2,6997500,false
o3,tx001,2,bc1change,2000000,true
```

## Relationships
```
Blocks
------
block_hash (PK)
      │
      │ 1:N
      ▼
Transactions
------------
tx_hash (PK)
block_hash (FK)
      │
      ├──────────────┐
      │              │
      │1:N           │1:N
      ▼              ▼
Inputs           Outputs
------           -------
tx_hash (FK)     tx_hash (FK)
```

## Generate realistic dummy data

To make your dataset feel realistic:

Generate a block every 10 minutes on average.
Give each block 1,500–3,000 transactions.
Give each transaction 1–5 inputs and 2–4 outputs.
Ensure the sum of outputs plus the fee equals the sum of inputs.
Reuse previously generated outputs as future inputs to mimic the UTXO (Unspent Transaction Output) model Bitcoin uses. This creates a realistic chain of spendable outputs rather than independent transactions.

That last point is especially valuable because it lets you demonstrate referential integrity, joins across tables, and richer analytics in your Spark transformations and Trino queries. It also means that if you later replace the generated CSVs with data exported from a real Bitcoin ETL pipeline, your Bronze, Silver, and Gold processing should require few or no structural changes.
